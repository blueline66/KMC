## Завдання 1. Картка TLS-сертифіката сайту

Об'єкт аналізу: інтернет-магазин (`rozetka.com.ua`).

| Поле сертифіката | Значення |
| :--- | :--- |
| **Домен (Subject / CN)** | `rozetka.com.ua` (та альтернативні імена `*.rozetka.com.ua`) |
| **Видавець (Issuer / CA)** | Let's Encrypt (E6 / R3) |
| **Термін дії (Validity)** | 10.02.2026 — 11.05.2026 |
| **Версія TLS** | TLS 1.3 |




## Завдання 2. Схема рукостискання TLS 1.3 та перевірка сертифіката

Процес встановлення захищеного з'єднання TLS 1.3 складається з наступних кроків:

1. **ClientHello:** Браузер надсилає серверу список підтримуваних версій TLS, шифрів та свій публічний ключ для узгодження.
2. **ServerHello + Сертифікат + Ключ:** Сервер обирає параметри з'єднання, надсилає свій цифровий TLS-сертифікат та власний публічний ключ.
3. **Перевірка сертифіката браузером:** Клієнт аналізує автентичність сертифіката:
   * **Перевірка домену:** Порівняння адреси в рядку браузера з доменом у сертифікаті. При невідповідності виникає помилка `NET::ERR_CERT_COMMON_NAME_INVALID`.
   * **Перевірка терміну дії:** Перевірка, чи поточна дата входить у діапазон дійсності. Якщо сертифікат протерміновано, виникає помилка `NET::ERR_CERT_DATE_INVALID`.
   * **Перевірка довіри до видавця:** Перевірка цифрового підпису Центру Сертифікації (CA). Якщо видавець невідомий або сертифікат самопідписаний, виникає помилка `NET::ERR_CERT_AUTHORITY_INVALID`.
4. **Підтвердження та шифрований обмін:** Браузер і сервер обчислюють спільний симетричний ключ сеансу та починають передачу зашифрованих даних.


## Завдання 3. Розбір сценарію атаки (Підміна DNS-відповіді / DNS Spoofing)

Атака підміни DNS-відповіді полягає у фальсифікації DNS-запитів клієнта, внаслідок чого замість справжнього IP інтернет-магазину користувач отримує IP-адресу фальшивого сервера зловмисника. Ця атака порушує властивості **Цілісності (Integrity)** та **Конфіденційності (Confidentiality)** триади CIA, оскільки користувач перенаправляється на підроблений ресурс і передає свої облікові чи платіжні дані зловмисникам. 

**Контрзаходи:**
1. **Використання протоколів DoH (DNS over HTTPS) або DoT (DNS over TLS):** Захищають і шифрують DNS-запити від локального перехоплення та модифікації.
2. **Перевірка TLS-сертифіката та використання HSTS:** Навіть при DNS-перенаправленні фальшивий сервер не матиме валідного TLS-сертифіката для оригінального домену, і браузер заблокує з'єднання.



## Завдання 4. Порівняння TLS і VPN

| Критерій порівняння | TLS (Transport Layer Security) | VPN (Virtual Private Network) |
| :--- | :--- | :--- |
| **Обсяг шифрування трафіку** | Шифрує лише **окреме з'єднання** конкретного додатка/браузера з конкретним сервером. | Шифрує **весь мережевий трафік** пристрою до VPN-шлюзу. |
| **Типовий сценарій використання** | Безпечний перегляд конкретного вебсайту (наприклад, здійснення покупки в інтернет-магазині). | Захищене підключення пристрою з незахищеної мережі (наприклад, публічний Wi-Fi) до корпоративної чи приватної мережі. |

## Контрольні запитання

1. **Які поля сертифіката перевіряє браузер під час TLS-з'єднання?**  
   Доменне ім'я (Subject/SAN), термін дії (Validity period), цифровий підпис видавця (Issuer/CA) та статус відкликання.
2. **Яку помилку покаже браузер при невідповідності домену сертифіката?**  
   Помилку `NET::ERR_CERT_COMMON_NAME_INVALID` (або "SSL certificate name mismatch").
3. **Чим VPN відрізняється від TLS за обсягом захищеного трафіку?**  
   TLS шифрує лише одне окреме сеансове з'єднання програми, а VPN створює тунель і шифрує весь трафік пристрою повністю.
